你的代码调用 `read()` 的时候，CPU 在执行什么、线程在等什么、数据又从哪搬到哪——这三个问题不搞清楚，BIO、NIO、io_uring 学到最后全变成背 API。这一篇从内核的角度把 I/O 的基本概念拆干净：数据路径、两阶段模型、阻塞 vs 非阻塞、同步 vs 异步，然后把两根轴叠回时间线看三种模型实际怎么跑，讨论为什么同步非阻塞统治了二十年，最后讲虚拟线程把哪一环改了、哪一环没动。

> 前置阅读：[网络通信基础]({{< ref "/posts/netty/network-explanation" >}}) — 建议先了解 TCP/IP 分层、Socket 系统调用和 TCP 连接状态后再读本篇，否则部分概念缺少上下文。

## 一、数据是怎么从网卡到你的代码的

理解 I/O 模型之前，先回答一个底层问题：网卡收到数据后，数据经历了什么才能被你的 Java 代码读到？

{{< diagram "data-flow.svg" "网络数据从网卡到应用程序的完整路径" "sm" >}}

看箭头的方向：数据从网卡开始，一层一层往用户空间走。整个过程可以浓缩为两阶段：

| 阶段 | 做什么 | 谁来做 | 耗时由什么决定 |
|---|---|---|---|
| 阶段一：等待数据 | 网卡 → DMA → 内核协议栈 → Socket 接收缓冲区 | 内核 | 网络延迟 + 对方什么时候发 |
| 阶段二：拷贝数据 | 内核 Socket 缓冲区 → 用户空间 Buffer | 内核（`read()` 系统调用） | 通常几微秒到几十微秒 |

以下是一个 Java 应用调用 `read()` 的完整过程：

```
① 网卡收到帧，DMA 直接把数据写入内核环形缓冲区（不经过 CPU）
② 内核协议栈处理 IP/TCP 头，校验序列号，数据挂到对应 Socket 的接收队列
③ 应用程序调用 read(fd, buf, size)，CPU 从 Ring 3 切到 Ring 0
④ 内核把数据从 Socket 缓冲区拷贝到用户空间 buf
⑤ read() 返回，CPU 切回 Ring 3，buf 里已经有数据可用了
```

**任何 I/O 模型的本质区别，就是看这两个阶段中——线程在等还是不等、拷贝时线程是堵在内核里还是继续跑。**

## 二、用户空间与内核空间

{{< diagram "kernel-userspace.svg" "用户空间与内核空间的隔离和数据流动" >}}

操作系统把内存分为两个区域，中间有硬边界：

- **用户空间（Ring 3）**：你的 Java 程序跑在这里。Buffer、变量、对象都在这里。权限低，不能直接操作硬件，也不能直接读内核内存
- **内核空间（Ring 0）**：操作系统内核、驱动程序跑在这里。Socket 缓冲区、TCP 协议栈都在这里。权限高，可以直接访问硬件

两者之间的数据交换必须通过**系统调用**：`read()` 的本质是把数据从内核空间的 Socket 缓冲区拷到用户空间的 Buffer。这个拷贝需要 CPU 参与——CPU 要从用户态切到内核态执行拷贝代码，每次系统调用都伴随一次这样的**模式切换**（mode switch，~100ns，比线程切换轻量得多）。

但 BIO 模型的真正开销不在这里，而在线程级别的**上下文切换**：一个连接一个线程，所有线程各自堵在 `read()` 上。数据到达时，内核要在这些线程之间来回切换——这才是 `vmstat` 的 `cs` 列统计的东西，每次 ~3-5μs。用 `vmstat` 直观感受一下——`vmstat 1 3` 表示每 1 秒输出一次系统状态，连续输出 3 次。关注 `cs`（context switch）列：

```bash
vmstat 1 3
# 空闲的 Linux 桌面/服务器：cs 通常在几百到几千次/秒
```

换成 BIO 服务——每个连接一个线程，所有线程堵在 `read()` 上，用 `wrk` 或 `ab` 一压——同样是 `vmstat 1 3`，`cs` 列可能飙到几十万次/秒。每次 `read()` 返回都可能触发一次线程切换。

上下文切换不是免费的：每次切换，CPU 要保存当前线程的寄存器、程序计数器、栈指针，再加载下一个线程的。一秒几十万次切换，CPU 有相当比例的时间花在"换人"而不是"干活"上。后续讲 epoll 和 io_uring 时，核心优化目标之一就是减少这种切换。

## 三、阻塞 vs 非阻塞

这两个词描述的是**阶段一**的行为：数据还没到时，线程怎么办？

**阻塞（Blocking）**：数据没到 → 线程挂起，CPU 去跑别的任务。数据到了 → 内核唤醒线程 → `read()` 返回。

```java
byte[] buf = new byte[1024];
int len = in.read(buf);
// 数据没到 → 线程状态变为 TASK_INTERRUPTIBLE，让出 CPU
// 数据到了 → 内核把线程放回运行队列 → read() 返回实际字节数
```

**非阻塞（Non-blocking）**：数据没到 → `read()` 立刻返回 0 或 -1，线程不挂起。但线程需要不停轮询，直到数据到位。

```java
channel.configureBlocking(false);
int len = channel.read(buf);
// 数据没到 → 立刻返回 0，线程继续跑
// 数据到了 → 返回实际字节数
```

这两种策略没有绝对的好坏：阻塞让线程睡觉省 CPU 但占着线程资源（一个线程 ~1MB 栈），非阻塞不占线程但一直轮询浪费 CPU。**哪个更合适，取决于连接数和数据到达频率**——连接少、数据密集，阻塞省心；连接多、数据稀疏，非阻塞才能扛住。

> **但这里有一个很容易产生的误解**：如果只是把一个 socket 设成非阻塞然后裸轮询，线程确实不挂起了——但它会变成死循环，每秒几十万次 `read()` 返回 0，CPU 100% 空转。**裸非阻塞本身没有工程价值。**

非阻塞的真正用法是配合**多路复用（epoll）**：把成百上千个 socket 注册到一个 epoll 实例上，线程堵在唯一的 `epoll_wait()` 里睡觉。哪个 socket 的数据到了，内核就唤醒线程，返回就绪列表。线程只需要处理那些真的有数据的连接。

所以非阻塞的核心价值不在"线程更自由了"——epoll 里的线程在 `epoll_wait()` 上也是堵着的——而在于 **"一个线程就能管几万个连接"**。阻塞模式下 1 万个连接需要 1 万个线程（~10GB 栈内存），epoll 模式下一个线程就够了。这才是同步非阻塞统治二十年的根本原因，第六节会展开讲。

## 四、同步 vs 异步

这两个词描述的是**阶段二**的行为：谁来执行数据拷贝？

**同步（Synchronous）**：线程自己调用 `read()`，自己等着内核把数据拷到用户空间。拷完 `read()` 才返回。返回时数据已经在用户 Buffer 里。

**异步（Asynchronous）**：线程告诉内核"给我读数据"，然后立刻返回继续干别的。内核在后台把数据从 Socket 缓冲区拷到用户 Buffer，全部完成后通知线程。`read()` 返回的时候数据可能还在路上。

区分的关键准则：**看调用者发起的读操作什么时候返回，以及返回时数据是否已经在用户空间。**

| | 同步 | 异步 |
|---|---|---|
| `read()` 什么时候返回 | 数据拷到用户空间后 | **立刻返回**，拷贝由内核后台完成 |
| 返回时数据在哪 | 已在用户 Buffer | 不确定，内核后面会通知 |
| 典型 API | `read()`, `recv()`, `recvfrom()` | `aio_read()` (POSIX AIO), `io_uring` |

## 五、四张流程图：把两根轴叠起来看

阻塞和非阻塞管阶段一（等不等），同步和异步管阶段二（谁拷）。单独说都懂，叠在一起就乱了。下面四张流程图用同一个结构——调用读操作 → 阶段一 → 阶段二 → 数据可用——把四种组合的实际跑法画出来。**看每张图只需盯三个问题：线程什么时候堵了、拷贝是谁做的、读操作什么时候返回。**

### 第一张：BIO —— 同步阻塞

{{< diagram "io-bio-flow.svg" "BIO 同步阻塞：线程调用 read() 后，在阶段一挂起等数据，阶段二参与拷贝，全程阻塞" >}}

对照第三节的定义来看：**阶段一 没数据 → 阻塞**，线程挂起，内核等。对照第四节：**阶段二 拷贝 → 同步**，线程自己参与拷贝，`read()` 在拷贝完成后才返回。

这张图解释了一个常见的困惑：BIO 的"一个连接一个线程"不是因为线程在做计算，而是线程在阶段一 卡着动不了。10 个连接就需要 10 个线程各自卡着，哪怕 CPU 闲到 1%。**阻塞带来的浪费不是 CPU，是线程栈内存（每个 ~1MB）**。

### 第二张：NIO —— 同步非阻塞

{{< diagram "io-nio-flow.svg" "NIO 同步非阻塞：线程反复调用 read()，前 N 次立刻返回 0，最后一次执行阶段二 同步拷贝" >}}

和 BIO 对比看分岔点：阶段一 的处理完全不同——没数据时不堵，`read()` 直接返回 0。线程可以立刻去问下一个连接（这是 epoll 之所以能单线程管几万连接的基础）。

但注意阶段二：**蓝色的拷贝框和 BIO 一模一样**。数据到了之后，线程还是自己要参与拷贝。"同步非阻塞"这个名称准确地说了两件事——阶段一 非阻塞、阶段二 同步。只改了一半，没改另一半。

> **追问：`select()` 本身也是阻塞的，那和 BIO 有什么区别？** 区别在线程和连接的关系变了。BIO 是"一个连接堵一个线程"，epoll 是"一个线程替所有连接统一堵"。这个线程确实不能同时做计算任务——它在事件循环里，等的间隙才能处理业务逻辑——但它一个人顶了一万个人的岗。非阻塞的"自由"指的不是线程有空干别的，而是**不需要一万个线程来扛一万个连接**。

### 第三张：AIO / io_uring —— 异步非阻塞

{{< diagram "io-aio-flow.svg" "AIO/io_uring 异步非阻塞：线程提交请求后继续执行，内核后台完成等数据+拷贝，写 CQ 通知" >}}

和前两张的根本区别：阶段二 的拷贝框不在线程这边，在内核后台那条分支里。线程只做了两件事——交任务、最后看一眼结果。中间的等待和拷贝，线程完全不参与。

代价也在这张图里：注意右下角的 CQ（Completion Queue）。线程不能假设数据立即可用——它需要在"忙完了"之后主动去检查完成事件。编程模型从"一条直线"变成了"提交 → 干别的 → 回来查结果"，调试和理解都更费劲。但这是三个模型里唯一一个全程零阻塞的。

### 第四张：异步阻塞 —— 为什么没人用

{{< diagram "io-async-blocking.svg" "异步阻塞：线程调用异步 API 后立刻返回，然后自己调 sem_wait 堵着等——效果等同于同步阻塞" >}}

异步阻塞这个模型正好可以用来检验你是不是真的把两个维度分开理解了。注意：这里的"阻塞"和第三节定义的不是同一件事——`aio_read()` 本身在阶段一确实不阻塞（立刻返回了），但线程紧接着主动调了 `sem_wait()`，一个用户态的同步原语，把自己挂起来等内核的通知。**两个维度是正交的**：你可以选异步（外包拷贝），同时选阻塞（自己堵在完成通知上）。

结果看图：线程那条线往左拐进"堵着等"，和右边的内核后台工作形成并行——线程在"白等"，内核在干活。右下角红色框的质问就是结论：**既然最后还是堵着等，不如直接用同步 `read()`，效果一样、少一层 API。**

## 六、为什么同步非阻塞统治了二十年

把四张流程图压回两个维度，就是四象限：

{{< diagram "io-quadrant.svg" "同步/异步 × 阻塞/非阻塞 四象限" "md" >}}

| | 同步（阶段二：线程自己拷） | 异步（阶段二：内核后台拷） |
|---|---|---|
| **阻塞（阶段一：等着）** | **BIO**，全程堵 | **异步阻塞**，上述结论——等于同步阻塞 |
| **非阻塞（阶段一：不等）** | **NIO / epoll**，仅阶段二 ~5μs | **AIO / io_uring**，全程不堵 |

看到这个表，你可能会问：左下角（同步非阻塞）的阶段二明明还是堵的，为什么不直接用右下角（异步非阻塞），让内核全程包办？

答案很现实：**Linux 上真正的异步 I/O，在很长时间里就是个空壳子。**

POSIX AIO（`aio_read`）从调用线程的角度看确实是异步——`aio_read()` 立刻返回，调用线程不参与拷贝。问题出在实现方式上：**glibc 在用户空间用线程池来模拟异步**——每提交一个 `aio_read()`，glibc 就派一个后台线程去执行同步的 `pread()`。结果呢？1000 个并发请求背后还是 1000 个线程各自堵在 `read()` 上，只是线程从用户主线程换成了后台线程。**异步的 API，同步的实现——线程数一个没少。** 至于 Linux 内核自带的 `io_submit`（libaio）——它确实是真异步，但设计上只支持 `O_DIRECT`（绕过页缓存），基本上只能给数据库和存储系统用，网络 I/O 沾不上边。直到 io_uring（Linux 5.1，2019 年）才提供了从硬件到用户空间、同时覆盖网络和文件的端到端异步路径，真正算得上"生产可用"已经是 2020-2021 年的事。

所以 2019 年之前，**同步非阻塞就是 Linux 高性能网络编程的唯一正道**——早期用 `select()`/`poll()`（2002 年之前），后来用 epoll（2002 年随 Linux 2.5.44 引入）。Java NIO、Netty、Nginx、Redis 全部走这条路：

1. `select()` / `epoll` 告诉你哪个连接就绪了 → **阶段一不阻塞**
2. 调用普通的 `read()` 把数据拷出来 → **阶段二同步拷贝**

阶段二的 ~5μs 堵一下，跟阶段一的毫秒级网络等待相比，完全可以忽略。

Java NIO（`Selector`）的位置就是**左下——同步非阻塞**：`select()` 管阶段一，`read()` 管阶段二。io_uring 出现后，右下角的真·异步非阻塞才从理论走进生产。

## 七、虚拟线程改变了什么

JDK 21 引入虚拟线程（Virtual Threads），让"阻塞"这件事的代价变了。

传统 BIO 的痛点不是 `read()` 阻塞本身——阻塞时线程睡着不消耗 CPU，这没问题。真正的问题是阻塞时那个线程**占着昂贵的平台线程**（~1MB 栈），别的任务用不了它。虚拟线程把"线程"和"平台线程"解耦了：

```java
// JDK 21+
Thread.startVirtualThread(() -> {
    int len = in.read(buf);
    // read() 依然阻塞！
    // 但阻塞时 JVM 把平台线程从此虚拟线程身上卸下来，去跑别的虚拟线程
});
```

对比：

| 维度 | 平台线程 | 虚拟线程 |
|---|---|---|
| 内存占用 | ~1MB（栈） | ~1KB（对象头 + 少量 field） |
| 创建上限 | ~1 万（受限于内存） | ~百万 |
| `read()` 阻塞时 | 平台线程挂起，谁也得不到它 | 平台线程被卸下来，立刻挂到其他虚拟线程上 |
| 调度者 | OS 内核 | JVM（ForkJoinPool） |

**虚拟线程有它的适用边界**。计算密集型任务不适合——线程不阻塞就不会释放平台线程，虚拟线程的优势出不来。另外需要注意：`synchronized` 块内的阻塞可能短暂 pin 住平台线程（卸不下来），JDK 24 已通过 JEP 491 大幅缓解此问题。
