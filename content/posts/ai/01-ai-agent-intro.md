## 核心观点

本章是全书的概念地图，用一个公式 **Agent = LLM + 上下文 + 工具** 串起整个 Agent 世界，并指出真正决定产品竞争力的是模型之外的 **Harness 工程**（Harness 原指套具/马具，这里借指包住模型、让模型真正能用的那层工程）。

## 核心内容

### 1. 核心公式的三个层次

同一个 Agent 可以用三种语言描述：

| 层次 | 表述 | 含义 |
|------|------|------|
| 直觉层 | 大脑 + 眼睛 + 手脚 | LLM 思考决策，上下文决定看到什么，工具决定能做什么 |
| 实现层 | LLM + 上下文 + 工具 | 工程组件的最小组合 |
| 学术层 | 策略 (Policy) + 观察空间 (Observation Space) + 动作空间 (Action Space) | RL 形式化语言 |

其中 **策略**对应"大脑"（由 LLM 承担）；**观察空间**对应模型能看到的数据（由上下文承载），对应直觉层的"眼睛"；**动作空间**对应模型能执行的操作（由工具承载），对应直觉层的"手脚"。

关键边界：这个公式只描述 **Agent 边界之内** 的实现，**不包含 Environment**。环境（文件、数据库、网页、用户、其他 Agent、物理世界）位于 Agent 之外，是与 Agent 交互的另一方。

### 2. 观察空间与动作空间：最被低估的能力杠杆

> **在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往是重新定义或扩展观察空间与动作空间。**

作者举了两个有说服力的产品案例：

- **Manus**：没有靠换更强模型成为通用 Agent，而是把 Deep Research（调研）、Coding（代码）、Computer Use（操控）三者的观察/动作空间取**并集**。
- **OpenClaw**（一个本地优先的开源个人 Agent 项目）：通过 WhatsApp/Telegram/Slack 等消息渠道 + 本地网关（Gateway）连接 Google Drive、Notion，把分散在用户数字生活中的文件都纳入同一观察空间。

**很多"需要更聪明模型"的问题，其实只是接口问题**——把数据纳入上下文、把操作封装成工具，原本不可解的任务就可能变得可解。

### 3. 上下文 = 静态前缀 + 轨迹

每次调用 LLM 的上下文由两大类内容构成，合起来共五个部分：

- **静态前缀**：系统提示词（岗位说明书）+ 工具定义（声明可用工具）
- **轨迹（trajectory，动态消息历史）**：用户消息 + 模型回复（reasoning/content/tool_calls）+ 工具执行结果

消融实验（实验 1-1，即逐个删掉某个组件、观察后果）揭示各组件**并不等价**：

- 去掉**工具定义** → 模型失去行动能力，但**不会沉默**，反而给出一份格式工整、数据来自参数记忆的"看似正确"答案；
- 去掉**工具执行结果** → Agent "盲目"执行，反复重试直到耗尽迭代预算；
- 去掉**思考过程 (reasoning)** → 只要下一步决策仍能从工具执行结果推导出来，几乎无代价；
- 去掉**历史消息** → 模型忘记已执行过的操作，重复调用、反复犯同样的错误。

**核心洞察："给出了回答"不等于"完成了任务"**——上下文残缺时的典型失败不是报错，而是毫无破绽的假答案。

### 4. ReAct 循环

"想 → 做 → 看"的循环，是 LLM、上下文、工具三者协同的核心机制。最小骨架：

```python
trajectory = [user_request]

repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)

    if decision has no tool call:
        return decision.answer

    for call in decision.tool_calls:          # 独立调用可并行
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

注意 `Harness.validate` 和 `Environment.execute` 是刻意分开的：Model 只负责决定下一步，Harness 负责组装上下文、校验调用，Environment 负责真正执行工具。

### 5. Harness 工程：模型之外的竞争力

生产形态下公式展开为：

```
Agent = Model + Harness
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent ⇄ Environment
```

五个要素分两组：**上下文管理与工具接口让 Agent"能做事"；约束预防错误、验证发现偏差、纠正把偏差改回来，三者构成"不做错事"的闭环。**

书中给出了一个极具说服力的数据：LangChain 在 Terminal Bench 2.0 上得分从 52.8% → 66.5%（从 30 名开外跃升至前 5），**改变的不是模型，而是 Harness**——让 Agent 自动检查执行结果、检测重复循环、优化思考策略。

工程范式演进弧线（层层包含，不是替代）：

```
提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程 ⊂ Graph 工程
```

其中 Loop 工程指把多轮循环结构化，Graph 工程指把多个 Agent 编排成图。

### 6. 编排模式：工作流 vs 自主 Agent

- **工作流**：预定义代码路径，确定性、安全（风险被限制在单个步骤内），但缺乏变通性。
- **自主 Agent**：执行路径由环境反馈实时决定，适合开放式问题，但成本高、有复合错误风险。
- **实践原则**：先优化提示词 → 再考虑工作流 → 最后才引入自主 Agent。**"Less structure, more intelligence"**——好的结构不是替 Agent 预演全部思考，而是守住边界，把边界内的决策空间还给模型。

### 7. 三层护栏（按攻击者绕过的难度递增，而非处理顺序）

| 层级 | 管什么 | 典型机制 |
|------|--------|---------|
| 上下文层 | 模型能看到什么 | 相关性/安全分类器、内容审核、规则保护、指令与数据分离 |
| 执行层 | 模型能做什么 | 工具风险评级、独立审查进程、最小权限、人在回路、PII 过滤器 |
| 数据层 | 世界最终能被改成什么样 | 行级安全、约束与校验器、受控视图、不可伪造的访问上下文 |

**核心判断：处在同一上下文里的 Agent 很难判断自己是否已被提示注入（prompt injection，攻击者把恶意指令混入输入）**，所以上下文层只能降低攻击成功率，给不出保证——这就是必须有下面两层的原因。

## 贯穿全书的五个设计模式

1. **提议者—审核者（Proposer-Reviewer）**：产出与评判由两个不共享上下文的角色承担（自审不可靠）。
2. **渐进式披露（Progressive Disclosure）**：先给可检索目录，再按需加载细节。
3. **只增不改（Append-only）**：状态只追加不回头改，换取可缓存、可重放、可审计。
4. **边界集 + 保留集（Boundary Set + Retention Set）**：任何修改都要同时验证"该变的"和"不该变的"。
5. **最小 diff + 可回滚**：每次修改尽量小、带来源、可单独回滚，让归因成为可能。

## 代码示例：ReAct 轨迹结构示意

```text
轨迹 = [
  {role: "user", content: "计算 Q1-Q4 季度收入总和与平均（多币种）"},

  # 第 1 次迭代：模型决定并行转换货币
  {role: "assistant", reasoning: "需要统一换算为 USD...", content: "",
   tool_calls: [
     {name: "convert_currency", args: {amount: 2100000, from: "EUR", to: "USD"}},
     {name: "convert_currency", args: {amount: 1800000, from: "GBP", to: "USD"}},
     {name: "convert_currency", args: {amount: 380000000, from: "JPY", to: "USD"}}
   ]},
  {role: "tool", content: "EUR->USD: 2282608.7"},
  {role: "tool", content: "GBP->USD: 2278481.01"},
  {role: "tool", content: "JPY->USD: 2541806.02"},

  # 第 2 次迭代：模型决定用代码求和
  {role: "assistant", reasoning: "已获得转换结果，用代码汇总...", content: "",
   tool_calls: [
     {name: "code_interpreter", args: {code: "total = 2500000 + 2282608.7 + ..."}}
   ]},

  # 第 3 次迭代：生成最终答案
  {role: "assistant", reasoning: "计算完成，总结...", content: "FINAL ANSWER: ..."}
]
```

## 阅读与思考

**1. "Harness 工程"是我认为全书最有价值、也最反直觉的判断。**

过去一年（2025—2026）Agent 领域最明显的变化，是模型的工具调用能力正被 RL 内化为"原生能力"——Kimi K3 连续 200～300 次工具调用保持稳定、GPT-5.6 在服务端闭环跑完整个 Deep Research 编排。表面看，这似乎意味着"框架会越来越薄、Harness 会消失"。但本书的立场更精确：**模型会持续内化的，只是 Harness 里的"适配层"**（提示技巧、解析容错这类脚手架），而安全边界、审计、业务规则这些**硬约束**不在模型能内化的范围内，会长期留在 Harness 里——"Harness 会消失"其实是被夸大的结论。

我认可这种观点。一个能跑的 ReAct Demo 和能交付的生产系统之间，隔着的从来不是模型能力，而是约束（权限、熔断）、验证（审计）、纠正（失败重试、回滚）这些工程细节。当各家模型能力趋同，这些"模型之外"的工程细节反而成了真正的护城河。LangChain 不换模型只优化 Harness 就从排行榜 30 名外冲到前 5，是最好的注脚。

**2. 合并"看到的数据"与"能做的操作"，解释了为什么很多产品"一夜之间变强"。**

我过去习惯把 Agent 产品能力的差异归因于模型档次。本书纠正了这个归因偏差：Manus 的突破首先是"把三个原本分离的观察/动作空间合并"——**观察空间是模型能看到的数据，动作空间是模型能执行的操作**——而不是换了个更聪明的模型。这让我重新审视工具设计的常见误区——很多 Agent 项目缺的不是更好的模型，而是**没把任务所需的数据放进上下文、没把所需的操作封装成工具**。这是一个成本极低、收益极高的优化方向。

**3. "给出了回答 ≠ 完成了任务"是消融实验里最扎心的一课。**

上下文残缺时，模型不会报错退出，而是给出一份排版工整、语气笃定、但数据来自参数记忆的假答案。这一点对真实业务尤其危险——客服 Agent 或财务 Agent 一旦在缺上下文时"自信地编造"，损失是真实的。它提醒我：**验证闭环（工具结果回传）的价值，不在于让模型更聪明，而在于让它"知道自己不知道"**。

**4. 关于 Harness 复杂度的提醒很有分寸感。**

本书一边论证 Harness 是核心竞争力，一边又提醒这个结论最容易被误读：**Harness 很重要，不等于越复杂越好**。书中提出的 "Less structure, more intelligence" 是很好的平衡点（Manus 就是范例）：程序只固化权限控制、原始材料保护、原子发布这类**必须永远成立**的边界，其余决策空间还给模型。这避免了很多人一上来就画出一条"切分→提取→核验→解析→合并"的复杂流水线，结果架构越来越重、通用性越来越差。

**5. 模型持续内化 Harness 适配层，方向没错，但节奏慢得多。**

书中的提醒依然务实：模型训练以月为单位，无法一次内化真实业务里的全部约束与偏好。所以 Harness 工程师的价值不会随模型升级而归零，只会"职责下移"——从补模型短板，转向守住安全边界、审计、可回滚这些模型始终无法自我担保的底线。
