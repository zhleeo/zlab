## 核心观点

上下文是 Agent 的"眼睛"，而上下文工程是全书最关键的一章。这一章的骨架可以用四个要点概括：

- **核心命题**：上下文决定 Agent 能力上限。
- **底层事实**：上下文就是消息列表（公式：**上下文 = 静态前缀 + 轨迹**）。
- **硬约束**：KV Cache——静态前缀可缓存复用、动态轨迹只增不改。
- **另一条主线**：上下文学习本质是检索而非推理——模型擅长在已有内容里"查找"，却不擅长主动"归纳统计"。

提示工程与 Skills 决定往上下文里放什么，状态栏与压缩则是给上下文窗口这台"只有一半的检索引擎"补上缺失的"提炼层"。

## 核心内容

### 1. 上下文决定 Agent 能力上限

模型要执行具体任务，需要它根本不知道的背景信息（产品架构、业务规则、内部约定）。作者用"天才工程师加入新团队"作比：**模型智力只是基础，上下文质量才是 Agent 能力的真正关键**——一个中等模型配上精心组织的上下文，往往胜过顶级模型在信息匮乏下的盲目摸索。

而且这不只是技术问题，更是**组织问题**：

> **对远程工作友好的团队，往往也对 AI Agent 友好。**

Linux 内核这样文档驱动的开源项目天然适合 Agent 工作，因为信息是公开、可检索、结构化的。**AI Agent 就像一个永远的新员工**——所以构建 AI 原生团队，首先是一场文档化运动。

OpenAI 研究员翁家翌把这层意思说得最透：**"人和模型一样，最重要的是 Context。"** 他举例说，自己在 OpenAI 的工作也没那么难，换一个人只要有他全部的 context 一样能干；而"团队合作中最大的问题也是 context 的不一致"，"AI 短时间内无法取代人的最大原因也是 context——因为 AI 跟人并不在同一个环境里"。这恰好点出上下文工程要解决的核心问题：把 Agent 需要的背景信息系统化、结构化地送到模型面前。

### 2. 上下文就是消息列表：API 的四种角色

以 Chat Completions API 为例，请求核心是一个 messages 列表：

| 角色 | 来源 | 含义 |
|:-----|:-----|:-----|
| `system` | 开发者编写 | 身份、行为规则、约束（最高优先级，通常一条、放最前） |
| `user` | 终端用户 | 用户请求 |
| `assistant` | 模型生成 | 之前的回复（文本 + 工具调用请求） |
| `tool` | 框架执行 | 工具执行结果，通过 `tool_call_id` 关联 |

工具定义（tools）作为请求的**独立字段**（而非消息）传入。

**关键事实：模型 API 是无状态的**，每次调用都必须由 Agent 框架重新构造完整上下文。ReAct 论文的定义 `c_t = (o_1, a_1, ..., o_{t-1}, a_{t-1}, o_t)` 说明：Agent 的下一步行动取决于**截至当前的完整交互上下文**，而非眼前这一条输入。

### 3. KV Cache：上下文设计的底层约束

KV Cache 是推理时缓存已算 token 的键值对、避免重复计算的机制。理解它和 Chat Template 之后，可以提炼出三条对上下文设计的硬约束：

1. **静态前缀保持不变**：系统提示词、工具定义等放在前面且不随轮次变化的部分，可以被缓存复用，显著降低每轮推理成本。
2. **动态信息追加到末尾**：新观察、新工具结果永远 append 在末尾，而不是插入或修改前缀——改动越靠前，作废的缓存越多（对应"只增不改"模式）。
3. **使用标准 API 格式**：遵循厂商规定的消息结构，让 Chat Template 把消息翻译成模型训练时见过的固定 token 序列；自行拼接字符串会偏离训练格式，削弱多步思考能力。

这解释了为什么"工具 schema 动态加载到上下文末尾"（而非插回前缀）会成为 2026 年以来的新实践——它在不破坏前缀缓存的前提下实现了渐进式披露。

这里需要澄清一个原文强调的区分：**KV Cache** 与 **Prompt Cache** 是两个层级——前者是模型内部在单次推理中缓存已算 token 的键值对，后者是 API 服务商在多次请求之间复用相同前缀的跨请求缓存。"改前缀会作废缓存"的场景主要发生在 Prompt Cache 层，但两者都基于"前缀不变"，工程纪律一致。

更重要的是，**缓存不只是性能优化，而是架构约束**。原文用 Claude Code 的实践说明：当 Prompt Cache 的经济收益足够显著时，缓存一致性会反过来主导架构选择——

- **提示词结构由缓存边界决定**：系统提示词被一个缓存边界标记分成两半，标记之前可跨用户/会话全局缓存，标记之后放用户和会话特有信息。动态元素（OS 类型、模式开关、语言）一旦放到边界之前，就会让缓存键的变体数量翻倍（N 个二值条件 = 2^N 种组合），所以都要放到边界之后。
- **子 Agent 必须与父 Agent 字节级对齐**：子 Agent 的提示词、工具定义、模型配置、消息前缀、思考配置逐字节匹配，才能命中父 Agent 的 Prompt Cache。
- **工具结果的替换字符串首次出现即冻结**：大工具输出被替换成摘要预览后，替换字符串会被持久化，后续会话重启也复用同一串，避免缓存失效。

最深的一层是 Anthropic 的"保留思考"（preserved thinking）机制：服务端把每个思考块绑定到产生它的前缀上，前缀一改，这个思考块及其后所有思考全部失效，模型只能从头想起。于是**"只追加、不改写"就从性能建议升级为正确性要求**——新指令用追加的 system 消息、环境变化写进最新一轮、工具增删用专门消息块声明，而不是去改 tools 数组。

因此缓存经济性不是事后优化，而是前置约束：越早纳入架构设计，后续工程代价越小。

### 4. 提示工程与提示注入攻防

提示工程的核心对象是系统提示词。书中用消融实验给出两个硬证据：**信息组织混乱（拆散流程、去除层次）会让任务成功率下降 30% 以上；移除工具描述会让工具调用错误率增加 45%**。由此引出两条原则：

- **流程驱动优于规则堆砌**：把零散规则组织成清晰的 SOP（校验 → 分类 → 预处理 → 执行 → 验证），让模型随时知道自己在哪个阶段、下一步做什么，而不是在几十条规则里找匹配。
- **业务规则要细化到可执行**：模糊规则（"根据情况选计费类型"）会让行为不可预测，必须写死边界（如"退款/取消订阅绝不用按省钱提成"）。在优秀的 Agent 公司里，提示词往往由产品经理设计，工程师只负责准确编码，不擅自决定业务逻辑。

工具描述同样关键：要回答"什么时候用"而不只是"能做什么"，要列出边界（做不到什么），参数描述用具体例子代替抽象规范。

提示注入（Prompt Injection）是上下文层的核心威胁——攻击者通过外部数据（网页、文档）间接操纵模型。防御要点：

- **指令 / 数据分离**：明确区分"指令"和"待处理数据"，用分隔符隔离；
- **来源标注**：为每段外部内容标注可信度；
- **结构性上限**：但处于同一上下文的模型很难判断自己是否已被注入。

### 5. Agent Skills：渐进式披露的落地

Skills 机制是"渐进式披露"最典型的形态：

- **元数据常驻**：每个 skill 在目录里只占几十个 token（名称、描述、触发条件）；
- **完整内容按需加载**：只有当任务真正需要时才读取正文。

这同时优化两件事——**上下文预算**（不全量常驻）与**选择精度**（元数据足够让模型判断何时加载）。2025 年以来 Anthropic 的 Agent Skills、Claude Code 的 skill 目录都是这一思路的工业实践。

### 6. Agent 状态栏：把隐式状态显式化

状态栏技术把 Agent 原本"隐式"的状态（任务进展、工具调用计数、环境观察）提炼为**显式元信息**，注入上下文末尾。它的理论基础正是"上下文学习是检索而非推理"：模型不擅长自己从原始轨迹里"数出"已经打了几次电话、还剩几个 TODO，但给它一条算好的状态栏，它一眼就能"检索"到这个结论。

书里的典型例子是客服 Agent 打电话：系统提示词规定每个商家最多打 3 次，但 Agent 往往数不清自己打了几次，于是又打第 4 次甚至陷入循环。当状态栏显式标注 `phone_call invoked 3 times (Xfinity: 3/3 max)` 后，模型立即停止拨打。实验显示，加了状态栏后，小模型的准确率可以接近前沿大模型，每次迭代的思考 token、延迟和成本都下降约一个数量级。

实现上有一个关键细节：状态栏在 API 层是作为一条 **user 角色消息**追加到上下文末尾，而不是修改开头的 system 消息——这正是"动态信息追加末尾、静态前缀不动"的 KV Cache 原则在状态栏场景的应用。

### 7. 上下文压缩策略

压缩不只是"窗口装不下"时才需要。原文给出三个动机：**控制长度与成本**（最直观）、**提升思考质量**（总结后的知识比原始形式更利于模型检索）、**缓解上下文焦虑**（模型在窗口将尽时会提前收尾）。其中第二点引出一个关键概念——**上下文腐化（Context Rot）**：窗口没满，但 Agent 突然"找不到"关键信息了，因为注意力被无关内容稀释。这解释了为什么"没满也要压缩"。

当轨迹增长时，压缩的思路有两条主线：

| 思路 | 做法 |
|:-----|:-----|
| 上下文感知压缩 | 把当前查询意图和已积累信息纳入压缩决策，生成有针对性的摘要（实验显示可减少 75% 以上 token 用量） |
| 生产级分层压缩 | 按信息保质期分五层：大工具结果落盘只留摘要预览、噪声直接删除、API 层微压缩、逐轮归档式摘要、LLM 全量压缩兜底 |

但更釜底抽薪的思路是**隔离优于压缩**：把"在代码库大范围搜索"这类会产生海量中间内容的子任务交给独立上下文的子 Agent，主 Agent 只接收几百 token 的结论摘要，让噪声从一开始就不进入主上下文。压缩是有损、需额外 LLM 调用的事后补救；隔离则让主上下文和 KV Cache 前缀完全不受影响。

## 阅读与思考

**1. "上下文就是消息列表"这个朴素事实，反而是最被低估的认知。**

很多人讨论 Agent 时喜欢谈"架构"、"编排"、"多 Agent"，却忽略了一个底层现实：**模型每次只能看到一个消息列表，无状态，全量重传**。理解这一点后，很多"玄学"问题都变得可解释——为什么工具描述写不好模型就乱调用？因为模型唯一的信息来源就是这个列表。为什么长任务会退化？因为列表里的有效信息被历史淹没。这让我在调试 Agent 时养成了一个习惯：**先看模型此刻实际"看到了什么"，再谈它"为什么做错了"**。

**2. KV Cache 是全书最"硬核"、也最实用的一节。**

大多数 Agent 教程完全忽略 KV Cache，但它是真实成本与延迟的决定因素。三条约束（前缀不变、追加末尾、标准格式）直接翻译成工程纪律：系统提示词要精心设计且保持稳定，动态内容永远 append。对照当前 Skills 机制把 schema 追加到末尾而非插回前缀的做法，可以清晰地看到"只增不改"这条设计模式是如何在性能层面落地的。

**3. "上下文学习本质是检索而非推理"——这是我读完最想划重点的一句话。**

它一句话解释了状态栏和压缩为什么有效：模型在一次前向传播里"查找"很强，但"归纳统计"很弱——上下文窗口像一台只有一半的检索引擎，没有提炼层。所以正确的做法不是塞更多原始信息让模型自己去"想"，而是主动把算好的结论（已打几次电话、还剩几个 TODO、目前已知什么）显式写进上下文。这个论断几乎推翻了我以前"信息越多越好"的直觉：**给模型的是"提炼后的结论"，而不是"让它去提炼的原料"**。

**4. 上下文工程本质是"组织工程"，这一点我认为是全书最深刻的洞察。**

书里那句"对远程工作友好的团队也对 AI Agent 友好"，点明了上下文工程的本质其实是组织文化问题。如果一个团队的架构决策散落在老员工的记忆里、业务规则靠口口相传、关键背景锁在私聊里，再强的模型也是"信息黑洞里的天才"。这解释了为什么同样的模型、同样的框架，在不同团队里 Agent 的效果天差地别——**差距不在模型，在上下文的可获取性**。这是很多团队引入 Agent 时最容易忽视、也最难补齐的一环。

**5. Skills 的渐进式披露是当下最活跃的工程方向，本书给了它清晰的理论坐标。**

2025—2026 年，Anthropic 的 Agent Skills、Claude Code 的 skill 目录、各类产品的"能力按需加载"，本质上都是同一件事：**元数据常驻 + 正文按需加载**。本书把这一机制的价值讲得很清楚——它不是简单地"省 token"，而是同时解决"上下文预算"和"选择精度"两个问题。理解了这一点，再去看各家的 Skills 实现，就不会停留在"这是个新功能"的表面，而是看到它背后的 KV Cache 约束和渐进式披露设计模式。

**6. 提示注入的"结构性上限"提醒我们：安全不能只靠提示词。**

书中诚实指出，处于同一上下文的模型难以自辨是否已被注入，所以上下文层的防御只能"降低成功率，给不出保证"。这正印证了第一章的分层防御原则——真正的兜底必须放在执行层（权限控制、沙盒隔离）和数据层。这个判断对做 Agent 产品的团队很重要：**不要在提示词里堆砌"忽略一切恶意指令"这类安慰剂式的防御，而要把安全落到权限、沙盒和数据结构上**。
